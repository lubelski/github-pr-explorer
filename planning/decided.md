# Decided

What is settled for github-pr-explorer. [PLAN.md](../PLAN.md) has what is being worked on and what is still open. [ideas.md](ideas.md) has ideas.

- The name is `github-pr-explorer`
  - The repo, the folder, and later the app and bundle all use it in full.
- It is a native Mac app
  - Swift, for the current macOS only. The owner asked for "fully native".
- It starts fresh
  - `github-pr-watch-menubar` is an earlier app on a related problem. The owner said on 2026-11-25 to set that work aside and not build on it. Nothing here depends on it.
- Design comes before code
  - The owner asked for ideas to be tried in Figma before anything is built. He reacted to the first rows on 2026-11-25, so building has started. He has not yet chosen between rows.
- Build on mock data first
  - The owner asked on 2026-11-25 for lots of mock data, to help work on the app and to get building started before sync exists.
  - The mock data is the same placeholder world the Figma rows use: the org `acme`, its repos and people, and pull request `acme/api #4826` as the worked example.
- The model is plain values in one core library
  - `GitHubPRExplorerCore` holds the models, the logic derived from them, the index protocol, and the mock world. It uses Foundation only and has no network code.
  - Every type is a `Codable`, `Sendable`, `Hashable` value. A `PullRequest` holds every section in one value: metadata and merge state, reviews and code owners, checks, files and commits, threads, and conversation comments and the timeline.
  - Each of those six sections carries its own `SectionProvenance`: a source (GraphQL API, REST API, local clone, push, web page, mock) and when it was fetched. Code owners count as reviews, commits as files, and conversation comments as timeline.
  - A file keeps its patch as GitHub's per-file text, hunks only. The parsed form, with old and new line numbers, is worked out on demand by `PatchParser` and is not stored.
  - A review request is pending by definition, because GitHub drops it once that reviewer reviews.
  - A thread on a removed line points at the old file (`side: left`), so the quoted line can always be found in the patch.
  - The index protocol is small and synchronous: all pull requests, one by id or by reference, the viewer, and a word search over title, number, author, repository and file paths. Each word must appear somewhere, ignoring case and accents. It is not the filter language.
- The mock world is fixed and deterministic
  - `MockWorld.standard` is seen from a fixed `now`, 2026-11-25T18:00:00Z. Two builds encode to byte-identical JSON, and a test checks it.
  - Randomness comes from a SplitMix64 generator written in the package, seeded per pull request from its reference, so adding one pull request never changes another. The standard library's random functions are never used, since their algorithms may change between Swift releases.
  - It holds the org `acme`, its repos `api`, `web`, `infra` and `docs`, 8 people who do most of the work, 22 who review now and then (so one pull request can ask 30 reviewers), three bots, and two agents with obviously placeholder logins (`example-agent-one`, `example-agent-two`). The viewer is Robin Quill (`robin-quill`), on `@acme/security`. The second team is `@acme/web-platform`.
  - It has exactly 218 open, 60 merged and 20 closed pull requests. `acme/api #4826` is written by hand to match the designs, and so are the 14 others the designs name. The rest are built from parts, with every status state in every repository, and the awkward cases views need: a 120-file pull request with a 5,000-line patch, a 287-event timeline, ci-bot's expensive-CI checkbox, empty and rich bodies, a very long title, non-ASCII text, 30 reviewers and none, 40 checks and none, renamed, removed, added and binary files, and outdated and resolved threads.
  - Its provenance uses the sources a real sync would use, with varied ages and some stale, so freshness views have something to show. `mock` is kept for data made up by a test or a preview.
  - When a view needs a case the world lacks, add it to the world in the same pull request.
- The status sentence has one precedence
  - A pull request's state is a symbol and one plain sentence, with every reason found. The first match wins: merged `✓`, closed `⊘`, draft `○`, in the merge queue `●`, blocked `✕` (merge conflicts or a failed required check, listing changes requested and unresolved threads too), changes requested `✕`, CI running `●`, checks queued `●`, a check that is not required failed `◐`, threads unresolved `◐`, waiting on reviewers or needs a review `◐`, behind the base branch `◐`, checking for conflicts `◐`, ready to merge `✓`.
  - Outdated threads that are not resolved count as unresolved, as GitHub's conversation rule counts them.
  - When a review is asked of the viewer or one of the viewer's teams, the sentence ends "Review requested from you." The comment on `StatusSentence` is the full rule.
- The command line tool starts with the mock world
  - `github-pr-explorer-ctl` lists pull requests, shows one, and exports the mock world. `list` prints tab-separated lines so agents can split them. `show --json` prints the same JSON the export writes.
  - The export writes `world.json` and one file per pull request under `pull-requests/`, named like `acme-api-4826.json`.
- A page layout is a JSON document
  - `PageLayout` has a format version, an id, a name, and tabs in order. A tab has a name and columns in order. A column has a relative width and blocks in order. A block placement is a block kind and a size, small or large. It is `Codable` and written with sorted keys, so the same layout is the same bytes.
  - The block kinds are description, checks, reviewers, owners touched, files, threads, activity, commits, and labels and metadata. An unknown kind fails to decode. A tab with no blocks is allowed.
  - A file that does not decode is reported with its file name, where in the file, and what is wrong, such as `decision-first.json, at tabs[0].columns[0].blocks[0].kind: unknown block kind "summary"`. The app shows the problem in the title bar and keeps going. When "Decision first" itself cannot be read, a copy compiled into the app is used, and a test keeps the two equal.
  - Layout rules and Edit Layout come later and build on this shape. The configuration folder reads layout files through the same decoding.
- Two layouts ship
  - "Decision first", after Figma row 1: one tab, two columns at widths 1.85 and 1. Left: Description, Threads, Files. Right: Checks, Reviewers, Owners touched, Activity.
  - "Tabbed", after Figma row 2: Overview (Description, Reviewers, Owners touched, Activity), Files (Files, Commits), Checks, Threads.
  - Both are JSON resource files in the core library, read through the same decoding a person's own file goes through. The layout menu at the right end of the title bar switches between them and the person's own layouts, for the open window only. Settings holds the default.
- The header is fixed above the tabs, for now
  - The repository and number, title, status sentence, and action buttons sit above the tabs and are not a block. This is temporary. `VISION.md` says no block has a fixed place, so the header becomes a block, or blocks, when Edit Layout arrives.
  - The action buttons are disabled with the tooltip "Not connected to GitHub yet". The line under them says why Merge is unavailable when it is.
- The page reads a fixed clock
  - The window measures every age from `MockWorld.now`, so it reads the same on every run. Freshness at the right end of the title bar is the oldest section's age, so it never claims more than is true, and its tooltip lists each section with its source.
- The main window has no footer, and status sits in the title bar (MAC-55)
  - The app's name is drawn once, centered. The system's own title is hidden with SwiftUI's `.toolbar(removing: .title)`, and the title bar helper hides it again if anything turns it back on, because SwiftUI can reset it on a `Window` scene's window after the helper last ran. Renders use a plain `NSWindow`, so they never showed the second title.
  - The right end of the title bar holds, right-aligned in quiet secondary text: the selected pull request's freshness (its tooltip lists each section's age and source), a warning when a layout file could not be read, the version, build and commit as `bundle.sh` stamps them ("0.1 (4) · b41c422"), and last a small menu that shows the current layout's name and lists the layouts. The update indicator sits between the version and the layout menu (MAC-47, below). Renders show a fixed "0.1 (0) · preview" so they read the same at every commit.
  - The layout menu is in the title bar for now. Edit Layout and layout rules may move it.
- The list has three fixed views (MAC-55)
  - "Needs my review": open pull requests where a review is asked of the viewer or one of the viewer's teams, never the viewer's own. "Mine": open pull requests the viewer wrote. "Everything open": every open pull request. Each shows its count within the search, and the search narrows within the chosen view.
  - They are plain predicates in the core library (`FixedListView`), not the filter language and not saved views. When the filter language arrives they become built-in filters written in it, and the type goes away rather than becoming a second way to write a condition.
  - The list starts in "Needs my review", because the vision is about deciding on pull requests and that view is the ones waiting on the viewer. The worked example, `acme/api #4826`, is in it. In the mock world the counts are 48, 12 and 218.
  - Changing the view keeps the open page, even when that pull request is not in the new view.
  - When the list is too narrow for the full names, the row uses short ones: "Review", "Mine", "All open".
- The list's width follows a drag on its trailing edge (MAC-55)
  - From 260 to 480 points, 300 by default. Double-clicking the edge puts it back to 300. In a small window the list gives way so the page keeps at least 600 points, without forgetting the width chosen.
- Window state is not configuration (MAC-55)
  - The list's width and the chosen view are remembered across launches in `UserDefaults`, as window state: where the person left the window. They are not settings, so they are not files in the configuration folder and not reachable from the command line or MCP. Anything that changes what the app does still belongs in the configuration folder.
- The diff is a stack of panes over the page
  - After Figma row 8 and the owner's note on MAC-53: the diff comes over the pull request without leaving it. Selecting a file in the Files block slides its diff in from the right, and a review thread slides in over the diff. Built for trial; the owner has not chosen between this and a diff tab.
  - The stack is `PaneStackPath` and `PaneStackLayout`, ported from `mac-os-agent`'s Settings, copied rather than shared. The page's blocks are the base. A path entry is `file:<path>` or `thread:<id>` (`PullRequestPane`).
  - The header (repository and number, title, status sentence, action buttons) is never covered. Panes cover the area below it, down to the window's bottom edge, since MAC-55 removed the footer. With a layout of tabs, the tab strip is part of what a pane covers, because the tabs choose blocks and the panes go over blocks. The pull request list stays as it is.
  - A pane is a card with a rounded top-leading corner and a shadow to its left, 10 points below what it covers. A covered pane is dimmed, does not scroll or take clicks, and is hidden from accessibility apart from a "Back to" button. A click anywhere on its strip goes back to it. The open file's row in the Files block stays marked.
  - Escape closes one pane, and so does the pane's back button ("‹ Pull request", "‹ Files"). With no pane open, Escape does what it did before. Panes slide with a 0.28-second spring with no bounce, or fade with Reduce Motion.
  - The panes belong to the selected pull request. Choosing another closes them.
  - Clicking a thread in the Threads block opens its file's diff with the thread on top, scrolled to its line. A thread whose file is not among the changed files does not open.
  - The thread pane is 420 points: the file and line, the quoted line, each comment with its author and age, and a Reply field with Resolve and Reply, disabled with "Not connected to GitHub yet".
- The diff pane's width rule
  - The page's strip is 300 points. It narrows to a 24-point sliver in side by side mode, with a thread open, or when a full strip and a 220-point file tree would leave the diff less than 720 points. Then the tree narrows to a 40-point rail, in side by side mode or when the full tree would still leave less than 720. The page gives way before the tree, as the oldest strip does in the stack. `DiffPaneLayout` holds the rule, and `PaneStackLayout` has the last word in a very narrow window.
  - At the app's default size, with the list showing, the page is a sliver even inline: 1,180 points less 300 and 220 is under 720.
  - The rail shows each file as a mark for its kind of change: a pencil for modified, plus for added, minus for deleted, an arrow for renamed, a picture for binary. Folders are separated by a line. The full path, kind and counts are in its tooltip, and the open file is filled with the accent color. Initials, as the Figma frame draws them, were left out as too cryptic.
- Inline and side by side
  - Inline is one column: old and new line numbers, then `−` or `+`, then the line. Removed lines are pale red and added pale green, and the symbol is always drawn beside the color. Hunk headers are shown as written.
  - Side by side puts the old file on the left and the new on the right. Inside a hunk, a run of removed lines pairs line for line with the run of added lines after it, and the longer run's extra lines face blank filler. Context lines face themselves. Each hunk's header shows its old and new line ranges.
  - Long lines scroll sideways and never wrap. The line numbers, markers and thread markers stay put and only the code moves, so in side by side both halves stay on screen and scroll together.
  - The diff is built once per file, off the main thread, from the parsed patch (`DiffDocument`), and kept while the window is open. Every row has the same height and width, so nothing is measured per row. The 5,000-line mock patch builds in about 20 milliseconds in a debug build.
  - Code is tinted on a best-effort basis, a line at a time, with no dependency: keywords, strings, comments and numbers for TypeScript-like files, and strings, numbers and `#` comments for YAML, Terraform and shell. Anything else stays plain.
  - A line with review threads shows "1 thread · Ada Park", the count and who started the first thread, at its end. It opens that thread. Binary files say "Binary file, not shown", a pure rename says so, and added, deleted and renamed files are tagged in the file header.
- A thread needs the viewer as code owner
  - Besides the viewer's own pull requests, threads they commented in, and mentions, a thread needs the viewer when a review is asked of them, or of a team they are in, and that person or team owns the thread's file by CODEOWNERS. So two of `acme/api #4826`'s threads, on `auth/` owned by `@acme/security`, need the viewer, and Max's on `api/routes/login.ts` waits on the author.
- Renders are drawn offscreen
  - `github-pr-explorer --render-previews <folder> [state ...]` builds the real window with the mock world's index and a model set to each named state, in a titled window that is never put on screen, and writes a PNG in light and in dark. It sets the activation policy to prohibited, so nothing appears and nothing takes focus. `scripts/render-previews.sh` runs it, stamped and signed as the bundle is, and can attach the PNGs to a pull request.
  - The states cover #4826 in each layout and tab, the diff pane in each mode and with a thread open, the 5,000-line file, renamed, binary, deleted and added files, the awkward mock cases, the list with a search, each list view, the list at its narrowest and widest, the smallest window, a bad layout file, and every block at both sizes, full and empty. The empty one is made up in the renderer with provenance `mock`.
  - Offscreen, a list's selected row does not draw, so the list draws it by hand while rendering.
- Configuration is a folder of plain files
  - Taken as a default on 2026-11-25, from the recommendations to open questions 11 and 12, pending the owner's answer. Built in MAC-56.
  - The folder is `~/Library/Application Support/github-pr-explorer/config/`. The app creates it on first run with `settings.json`, an empty `layouts/`, a `README.md` that explains each file, and a `.gitignore` for Finder and editor litter. Copies of the built-in layouts are not written: Duplicate to Edit makes one when asked.
  - `ConfigurationStore` in the core library is the only way in. The app, Settings and `ctl` all use it. Tests and renders pass a temporary folder and never touch the real one.
  - Nothing configurable lives only in the window or in preferences. The Settings window's selected section and its frame are window state, kept by the system as in the owner's other apps.
- The files are JSON, one file per thing, each with a format version and a schema
  - `settings.json` holds the general settings: `formatVersion`, `appearance` (system, light, dark), `defaultLayout`, `hidesBotEventsInActivity`, and `experiments`. Only `formatVersion` is required, and a key left out takes its default, so a person or an agent can write just the one setting they mean.
  - `layouts/<id>.json` holds one layout in the existing `PageLayout` format. The file is named after the layout's id, and an id is lowercase letters, digits and hyphens. A file with a built-in layout's id replaces it in place. The person's own layouts follow the built-in ones, by name.
  - A key the format does not have makes a file invalid, in settings and in layouts, so a misspelled key is reported instead of silently ignored. `$schema` is allowed at the top of a file for editors.
  - The schemas are hand-written in `schemas/`, with a description on every property. A test checks that their property names and enums match the Swift types, that the built-in layouts and the default settings pass, and that files the app refuses the schema refuses too. It uses a small checker for the keywords the schemas use, not a full JSON Schema validator.
- A file that does not validate is never applied
  - The last version of that file that worked stays in use: the one this run last read, or else the one in the last recorded version, so `ctl` and a relaunched app fall back the same way. A file wrong from the start is left out.
  - Each problem names the file, where in it, what is wrong, and whether the last good version is in use. Settings shows it in the section the file belongs to, the page footer counts layout problems, and `config validate` lists them and exits 1.
  - A default layout no layout has is reported but the file is still applied, with Decision first used instead.
  - Settings refuses to change `settings.json` while it has a problem, so a hand edit being fixed is never overwritten.
- Every valid change to the configuration is kept, whoever made it
  - The folder is a local git repository with no remote. After every valid change the store commits it, leaving out any file that did not validate. The message's first line says what changed and a `Changed-By:` line says who: `Settings window`, `edited on disk`, `ctl`, or `app`.
  - Git runs as `/usr/bin/git` with an identity passed on each command, the person's global and system git configuration switched off, and no hooks, so history neither depends on nor changes their git setup. Before running the macOS git stub, the store checks the developer tools are installed, so it never puts the install dialog in front of the person.
  - History never blocks a save. When git is missing or fails, the file is written, the problem is reported in Settings, History and Debugging, and the app carries on.
  - Restoring the folder or one file to a version writes the files as they were and records that as a new version, so the versions after it are kept. Changes on disk not yet recorded are recorded first.
- The app reloads the folder when a file changes
  - A folder watcher, after `mac-os-agent`'s, watches the folder, `layouts/`, and each file in them, so it sees a file replaced by an editor's save and a file written in place by a shell. Changes are gathered for 250 ms and then read once. The Settings window reads the folder again when it comes forward, in case an event was missed.
  - Every change reaches the open window at once: a new default layout switches it, the appearance applies to every window, and the Activity setting applies to blocks as they appear.
  - The layout menu in the window changes only the open window. Settings, a hand edit or `config set` holds the default, and the next change to the default wins.
- `ctl` reads and changes the configuration
  - `config path`, `validate`, `show [--json]`, `set <key> <value>`, `history [--limit N] [--json]`, `diff <version>`, `restore <version> [file]`, and `layouts list`, `show <id> [--json]`, `duplicate <id> <new-id> [--name]`. Each takes `--config <folder>`.
  - Commands that only look never create the folder or record a version. Commands that change something create the folder if needed and record their change as `ctl`.
  - MCP comes later. The agent rule in `AGENTS.md` still asks for it, so a later pull request adds the same operations over MCP.
- The Settings window has five sections
  - A SwiftUI `Settings` scene, so it opens with Command-comma and from the app menu, with the standard title bar. A fixed 200-point sidebar in a plain row, as `mac-os-agent` and `meeting-agenda-clock` have it, at 900 by 620 and resizable down to 760 by 480.
  - General: appearance, the default layout, and whether bot events start hidden in Activity. These are the settings that exist today. Nothing was added to fill the section.
  - Layouts: where the folder is, that a coding agent can edit it, and a button that copies its path. Each layout with a drawing of its first tab's columns and blocks, a strip for its tabs, its name, where it comes from, and which is the default. Set as Default, Duplicate to Edit, and for the person's own files Show in Finder and Delete. Files that failed are listed above with their problem.
  - History: the versions newest first, with what changed, who, and when. Selecting one shows its diff. Restore This Version and Restore One File ask first and say plainly that restoring adds a version and loses nothing.
  - Experiments: an `Experiment` enum in the core library, each case a switch that is off by default, saved in `settings.json`. It is empty. The sliding diff pane (MAC-53) landed on main while this was being built, as a feature that is always on. Putting it behind a switch that is off by default would have turned off work the owner had just merged, so it was left as it is. While it is empty the compiler warns that code using an experiment can never run, and the warnings go with the first case.
  - Debugging, always last, read-only: version, build and commit, what the mock world holds, the folder, whether it is watched, whether history works, the layouts, problems since launch, and Copy Diagnostics with the same as plain text.
- Pull requests are merged by whoever wrote them
  - The owner said on 2026-11-25 that sessions and their subagents may merge as they work, because the app has no users until he installs it.
- The vision and the plan are separate files
  - `VISION.md` holds what does not change. `PLAN.md` holds what does. The owner asked for this split.
- The repository is public (owner, 2026-11-25)
  - The owner made `lubelski/github-pr-explorer` public on 2026-11-25, which answers open question 8 in `PLAN.md`. Installed copies download the update feed and the zip from GitHub Releases without signing in, so it has to stay public.
  - Everything in it uses placeholder people and data. Check a diff for local paths, account names, and email addresses before pushing.
- Updates come through Sparkle (MAC-47)
  - Sparkle 2 from SwiftPM, linked by the app only. `AppUpdater.swift` is the one file that imports it. The signing key is the one all the owner's Mac apps share, and `scripts/sparkle-public-key.txt` holds its public half.
  - Only a release build updates itself. `scripts/release.sh` has `bundle.sh` write `SUFeedURL` (the latest release's `appcast.xml`), `SUPublicEDKey`, `SUEnableAutomaticChecks` and `SUAutomaticallyUpdate` into `Info.plist`. A plain `bundle.sh` build has no feed, so a development copy is never replaced.
  - A release build checks about once a day and downloads without asking. It does not relaunch on its own while the window is open, unlike `mac-os-agent`, which is a menu bar app. A downloaded update shows as "Restart to update" at the right end of the title bar, between the version and the layout menu. Clicking it relaunches into the update. Otherwise it installs when the app quits. An update found but not downloaded shows as "Update available", and clicking it opens Sparkle's window. When nothing waits, nothing extra shows. Below a 1200 pt window the indicator shows its symbol only, with the text in its tooltip.
  - **Check for Updates…** is in the app menu. Settings, General has an Updates group, shown only in a release build: **Update automatically** and **Check for Updates…** beside the version.
  - Update automatically is `updatesAutomatically` in `settings.json`, true by default, like every other setting: Settings writes it, and `github-pr-explorer-ctl config set updatesAutomatically false` changes it. The app copies it to Sparkle on launch and on every change. Sparkle keeps its own copy in the preferences, which the file overrides at the next launch or change.
- Releases are cut by `scripts/release.sh` (MAC-47)
  - It is `mac-os-agent`'s script with the names changed: `--check` says whether this Mac can release, `--dry-run` builds the zip and feed and publishes nothing, and `<version>` builds from `origin/main` with a clean tree, notarizes with the App Store Connect API key named in `~/.appstoreconnect/notary.conf`, staples, writes `appcast.xml`, tags `v<version>`, and publishes a GitHub Release with the zip and the feed.
  - `mac-app-release-poller` on the owner's Mac cuts releases when files that ship change on `main`. Adding this repo to it is the owner's step.
- Main is test-in-production until there are real users (owner, 2026-11-25)
  - The owner said: "We are going to use a 'test in production' posture until we have real users." A merge to `main` that touches shipping files reaches the owner's Macs within minutes, with no review gate. So `main` must always build, pass tests, and launch. `AGENTS.md` states the rule.
  - It ends when anyone other than the owner runs a release, and the rule is revisited then.
- The app icon is a branch that ends in a lens (MAC-47)
  - A white pull request branch whose head is a magnifier's lens, on a deep indigo gradient: a pull request, explored. It is apart from `github-pr-watch-menubar`'s white mark on green and `mac-os-agent`'s teal.
  - It is drawn in Swift in `AppIconDrawing.swift`, which keeps four candidates: a lens over a pull request mark, a stack of cards, the mark alone, and the shipped one. The mark alone was too close to `github-pr-watch-menubar`. The strokes are heavy so the branch and the lens still read at 32 px.
  - `scripts/render-icon.sh` writes `Resources/AppIcon.icon` and `docs/icon.png`, and `bundle.sh` compiles it with `actool`. A test checks every layer stays inside the safe area and that the committed icon is the shipped design.
