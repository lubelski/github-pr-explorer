# Decided

What is settled for github-pr-explorer. [PLAN.md](../PLAN.md) has what is being worked on and what is still open. [ideas.md](ideas.md) has ideas.

- The name is `github-pr-explorer`
  - The repo, the folder, and later the app and bundle all use it in full.
- It is a native Mac app
  - Swift, for the current macOS only. The owner asked for "fully native".
- It starts fresh
  - `github-pr-watch-menubar` is an earlier app on a related problem. The owner said on 2026-11-25 to set that work aside and not build on it. Nothing here depends on it.
- Design comes before code
  - The owner asked for ideas to be tried in Figma before anything is built. He reacted to the first rows on 2026-11-25, so building has started. He has not yet chosen between rows.
- Build on mock data first
  - The owner asked on 2026-11-25 for lots of mock data, to help work on the app and to get building started before sync exists.
  - The mock data is the same placeholder world the Figma rows use: the org `acme`, its repos and people, and pull request `acme/api #4826` as the worked example.
- The model is plain values in one core library
  - `GitHubPRExplorerCore` holds the models, the logic derived from them, the index protocol, and the mock world. It uses Foundation only and has no network code.
  - Every type is a `Codable`, `Sendable`, `Hashable` value. A `PullRequest` holds every section in one value: metadata and merge state, reviews and code owners, checks, files and commits, threads, and conversation comments and the timeline.
  - Each of those six sections carries its own `SectionProvenance`: a source (GraphQL API, REST API, local clone, push, web page, mock) and when it was fetched. Code owners count as reviews, commits as files, and conversation comments as timeline.
  - A file keeps its patch as GitHub's per-file text, hunks only. The parsed form, with old and new line numbers, is worked out on demand by `PatchParser` and is not stored.
  - A review request is pending by definition, because GitHub drops it once that reviewer reviews.
  - A thread on a removed line points at the old file (`side: left`), so the quoted line can always be found in the patch.
  - The index protocol is small and synchronous: all pull requests, one by id or by reference, the viewer, and a word search over title, number, author, repository and file paths. Each word must appear somewhere, ignoring case and accents. It is not the filter language.
- The mock world is fixed and deterministic
  - `MockWorld.standard` is seen from a fixed `now`, 2026-11-25T18:00:00Z. Two builds encode to byte-identical JSON, and a test checks it.
  - Randomness comes from a SplitMix64 generator written in the package, seeded per pull request from its reference, so adding one pull request never changes another. The standard library's random functions are never used, since their algorithms may change between Swift releases.
  - It holds the org `acme`, its repos `api`, `web`, `infra` and `docs`, a second org `globex` with `billing` and `docs` (MAC-111, so the list can be grouped by organization and two repositories share a short name), 8 people who do most of the work, 22 who review now and then (so one pull request can ask 30 reviewers), three bots, and two agents with obviously placeholder logins (`example-agent-one`, `example-agent-two`). The viewer is Robin Quill (`robin-quill`), on `@acme/security`. The second team is `@acme/web-platform`.
  - It has exactly 218 open, 60 merged and 20 closed pull requests. `acme/api #4826` is written by hand to match the designs, and so are the 14 others the designs name. Five open ones in `globex` are written by hand too, in place of the last five ordinary ones. The rest are built from parts, with every status state in every repository, and the awkward cases views need: a 120-file pull request with a 5,000-line patch, a 287-event timeline, ci-bot's expensive-CI checkbox, empty and rich bodies, a very long title, non-ASCII text, 30 reviewers and none, 40 checks and none, renamed, removed, added and binary files, and outdated and resolved threads.
  - Its provenance uses the sources a real sync would use, with varied ages and some stale, so freshness views have something to show. `mock` is kept for data made up by a test or a preview.
  - When a view needs a case the world lacks, add it to the world in the same pull request.
- The status sentence has one precedence
  - A pull request's state is a symbol and one plain sentence, with every reason found. The first match wins: merged `✓`, closed `⊘`, draft `○`, in the merge queue `●`, blocked `✕` (merge conflicts or a failed required check, listing changes requested and unresolved threads too), changes requested `✕`, CI running `●`, checks queued `●`, a check that is not required failed `◐`, threads unresolved `◐`, waiting on reviewers or needs a review `◐`, behind the base branch `◐`, checking for conflicts `◐`, ready to merge `✓`.
  - Outdated threads that are not resolved count as unresolved, as GitHub's conversation rule counts them.
  - When a review is asked of the viewer or one of the viewer's teams, the sentence ends "Review requested from you." The comment on `StatusSentence` is the full rule.
- The command line tool starts with the mock world
  - `github-pr-explorer-ctl` lists pull requests, shows one, and exports the mock world. `list` prints tab-separated lines so agents can split them. `show --json` prints the same JSON the export writes.
  - The export writes `world.json` and one file per pull request under `pull-requests/`, named like `acme-api-4826.json`.
- A page layout is a JSON document
  - `PageLayout` has a format version, an id, a name, and tabs in order. A tab has a name and columns in order. A column has a relative width and blocks in order. A block placement is a block kind and a size, small or large. It is `Codable` and written with sorted keys, so the same layout is the same bytes.
  - The block kinds are description, checks, reviewers, owners touched, files, threads, activity, commits, and labels and metadata. An unknown kind fails to decode. A tab with no blocks is allowed.
  - A file that does not decode is reported with its file name, where in the file, and what is wrong, such as `decision-first.json, at tabs[0].columns[0].blocks[0].kind: unknown block kind "summary"`. The app shows the problem in the title bar and keeps going. When "Decision first" itself cannot be read, a copy compiled into the app is used, and a test keeps the two equal.
  - Layout rules and Edit Layout come later and build on this shape. The configuration folder reads layout files through the same decoding.
- Two layouts ship
  - "Decision first", after Figma row 1: one tab, two columns at widths 1.85 and 1. Left: Description, Threads, Files. Right: Checks, Reviewers, Owners touched, Activity.
  - "Tabbed", after Figma row 2: Overview (Description, Reviewers, Owners touched, Activity), Files (Files, Commits), Checks, Threads.
  - Both are JSON resource files in the core library, read through the same decoding a person's own file goes through. The layout menu at the right end of the title bar switches between them and the person's own layouts, for the open window only. Settings holds the default.
- The header is fixed above the tabs, for now
  - The repository and number, title, status sentence, and action buttons sit above the tabs and are not a block. This is temporary. `VISION.md` says no block has a fixed place, so the header becomes a block, or blocks, when Edit Layout arrives.
  - The action buttons are disabled. The line under them says "Read-only for now", after why Merge is unavailable when it is, and the tooltip says this version reads pull requests and does not write to GitHub yet. It was "Not connected to GitHub yet" until MAC-69, which read as false once the data came from GitHub. One wording serves the mock world and GitHub.
- The page reads a fixed clock
  - The window measures every age from `MockWorld.now`, so it reads the same on every run. Freshness at the right end of the title bar is the oldest section's age, so it never claims more than is true, and its tooltip lists each section with its source.
- The main window has no footer, and status sits in the title bar (MAC-55)
  - The app's name is drawn once, centered. The system's own title is hidden with SwiftUI's `.toolbar(removing: .title)`, and the title bar helper hides it again if anything turns it back on, because SwiftUI can reset it on a `Window` scene's window after the helper last ran. Renders use a plain `NSWindow`, so they never showed the second title.
  - The right end of the title bar holds, right-aligned in quiet secondary text: the selected pull request's freshness (its tooltip lists each section's age and source), a warning when a layout file could not be read, the version, build and commit as `bundle.sh` stamps them ("0.1 (4) · b41c422"), and last a small menu that shows the current layout's name and lists the layouts. The update indicator sits between the version and the layout menu (MAC-47, below). Renders show a fixed "0.1 (0) · preview" so they read the same at every commit.
  - The layout menu is in the title bar for now. Edit Layout and layout rules may move it.
  - Since MAC-69 the layout menu is a cog with a menu, last at the right end: Layout as a submenu with the current layout checked, Sync Now (turned off unless pull requests come from GitHub, and it keeps to the sync's rate limit rules), Settings, and Check for Updates (turned off in a build that cannot update itself). The title bar no longer shows the layout's name.
  - Since MAC-69 the button that shows and hides the list sits in the title bar just after the window buttons, so it is there while the list is hidden. The search field has the list's full width.
- The list's tabs are saved filters (MAC-113, after the three fixed views of MAC-55)
  - The row above the list is Everything, first and fixed, then the saved filters marked to show as tabs, in the file's order, each with its count of open pull requests within the search. The chosen tab is filled with the accent color. Everything has no conditions and cannot be changed or removed.
  - The three fixed views, "Needs my review", "Mine" and "Everything open", are gone with `FixedListView`. Nothing is lost: the default saved filters are the first two, and Everything is the third. A test keeps each default equal to its old predicate, written out in the test. A window that remembered a fixed view opens on the saved filter that took its place, and a new one opens on Everything, as Figma row 11 draws it.
  - Tabs that do not fit, and saved filters not shown as tabs, sit in a » menu, which ends with Manage Saved Filters… (Settings on its Saved Filters section). The row measures each tab: it shows as many as fit with their counts, then as many with only the chosen tab's count, letting the last name give way before a tab is dropped. The chosen tab always shows, in the last place that fits.
  - Choosing a saved filter with a grouping sets the list's grouping. One without leaves the grouping alone. Choosing a saved filter that is not a tab, from the » menu, shows it as a temporary last tab with a dashed edge until another is chosen, with the same menu as any tab (Figma row 13 card, built as proposed).
  - A right-click on a tab offers Edit Filter…, Rename…, Duplicate, Remove from Tab Bar (Show in Tab Bar on a temporary tab), Delete… and Manage Saved Filters…; on Everything only the last (Figma row 13 card, built as proposed). A double-click on a tab edits it. A tab can be dragged onto another to take its place. Command-1 to Command-9 choose the tabs in order.
  - The chosen tab is window state, remembered by id in `UserDefaults`. Everything else about a saved filter is configuration.
- The Filter popover makes a filter on the spot (MAC-113, Figma row 11)
  - The filter button at the end of the tabs row, or Option-Command-F, opens it. It replaced the filter menu of MAC-69. It is 520 points wide: a fixed top with the title, Clear All and the filter in plain words; a middle that grows with the filter up to 380 points and then scrolls, with each set a rounded card of lines and a centered OR between cards; and a fixed footer with the count and its breakdown by status, "+ Add a Set", Save as Filter…, Cancel and Apply.
  - It starts from what the tab shows: the tab's saved filter, or the filter already applied on it. An empty filter shows a few one-click starts (waiting on me, by me, blocked, changes requested, not a draft) and a menu of fields.
  - A line is a field, "is" or "is not", and values as tokens joined by "or". "+ Add Condition" is a menu of fields, the ones the set does not use first, and a new line opens its value picker at once. The picker lists the field's values with how many open pull requests have each, ticks the chosen ones, narrows as you type, moves with the arrow keys and takes Return. For organizations, repositories and people it also takes a typed name the index does not hold yet, when the filter language accepts it. A line with no value yet, and a set with nothing finished, are left out of the filter, so adding a line changes nothing until it has a value.
  - The count follows every edit. Nothing in the list changes until Apply (Figma row 11 card, built as proposed). Cancel, Escape or a click outside discards.
  - The draft is `FilterDraft` in the core library: the filter language's sets and conditions with an identity each, for the views. It is not a second way to write a filter: its `filter` is the language's.
  - The menu's choices were `ListFilter`, whose clauses became the filter language's `FilterCondition` in MAC-112. Nothing in the window uses `ListFilter` any more. Its `ReviewState` is still the review state's vocabulary, and the rest is to go, with its tests.
- A filter applied and not saved lives on its tab (MAC-113, Figma row 11 card, built as proposed)
  - Apply replaces the chosen tab's filter in the list, so on a saved filter's tab the popover changes that filter's conditions in place, and on Everything it adds them. The tab shows an orange dot, and a line under the tabs says the filter in plain words, with Save… and Clear. The list never hides pull requests without saying so.
  - It is dropped on Clear, on choosing another tab and on quitting. Like the search, it is window state that is not remembered.
  - Save… asks for a name and, when the list is grouped, whether to keep the grouping, on by default. On a tab that is a saved filter it offers to update that filter or to save a new one, with Update chosen first (Figma row 11 cards, built as proposed). A new saved filter is the last tab and is chosen. Its id is made from its name.
- A saved filter is edited in a popover on its tab (MAC-113, Figma row 13)
  - It is the Filter popover's sibling and shares its parts: the name field where the title was, the same cards, and a strip with Group By (up to two levels, the list's own choices) and "Show in the tab bar". The footer has Delete Filter…, Cancel and Save. Delete asks in place, in the footer, and says History keeps the filter.
  - Saving writes `saved-filters.json` through `ConfigurationStore`, recorded as made by `main window`, a new author. When the chosen filter's grouping changes, the list follows it.
- Settings, Saved Filters manages the list only (MAC-113, Figma row 13)
  - It sits after Shorthands, so Experiments stays above Debugging, which is last. Everything is shown first, fixed. Each saved filter is a row with a handle to drag, a checkbox for "is a tab", the name with the filter in plain words under it, and its count. Rename… and Delete… act on the selected row, and on a row's right-click. A drag is one move and one version.
  - There is no condition editor and no way to make a filter there: a filter is made in the Filter popover (Figma row 13 card, built as proposed). Changes are recorded as made by the Settings window.
- The list can be grouped, as a tree of up to two levels (MAC-100, then MAC-111)
  - A group by button sits beside the filter button at the end of the views row. The button fills with the accent color while a grouping is on. Its menu is nested, after Figma row 9: under a "Group By" heading, None, then Organization, Repository, Author, Status and Review State, each opening a second menu. That menu's first item keeps one level ("Organization Only"), and under a "Then By" heading come the second levels. The second menu offers everything but the first level itself, and under Repository it leaves out Organization, since a repository has only one. Collapse All and Expand All end the main menu, turned off when they would change nothing. None is the default and is the flat list, with no title rows.
  - The grouped list is drawn like a file tree. Each group is a title row: a disclosure triangle at the leading edge, the group's name in semibold, and at the trailing edge how many pull requests it holds at any depth, in secondary color. A closed row keeps its count. Each level is indented 16 points, a pull request's row lines up with its title row's name, and a faint vertical guide line runs from under each open title row's triangle down past everything it holds. A long name gives way in the middle and the count never does. A group with no rows has no title row.
  - Under its organization a repository is named without it ("api"). Anywhere else it is named in full. A repository's or an author's title row takes its shorthand when one is set (MAC-73), with the full name on hover, and is still ordered by the full name. An organization has no shorthand kind yet, so its row keeps its name. A pull request's row does not repeat what its title rows say: inside a repository it reads "#4715 · you", inside an organization "api #4715 · you", and inside an author's row it leaves out the author. A shorthand takes the repository's or the author's place in a row as it does elsewhere, and stands alone, so inside an organization a repository with a shorthand reads "API #4715 · you".
  - A click on a title row selects it, like any other row. The triangle opens and closes it, and Option-click on a triangle does every row at that level, as in Finder. A double-click or Return opens and closes the selected title row. Left closes an open title row and otherwise selects the row that holds the selection; Right opens a closed title row and on an open one selects its first row. Up and down move through the rows on screen, title rows included, from the list and from the search field.
  - When a row closes over the selected row, by any means, the closed row becomes the selection, as in Finder, so the selection is always on screen. When the selection is made some other way, such as by the search field's arrow keys or a sync moving the selected pull request, the rows holding it open. While a title row is selected, the right side shows its overview (MAC-114, below).
  - Groups follow the filter menu's order for the same values: organizations by name, repositories by full name, authors with the viewer first ("Ada Park (you)") then by display name, statuses in the badges' order, review states in their own order. Status rows use the badge's long name, such as "Waiting on a review". Rows keep their order inside a group.
  - Grouping works inside the chosen tab, its filter and the search, and the tabs' counts do not change with it.
  - The grouping, the set of closed rows and the selection are remembered across launches in `UserDefaults` as window state, like the view. The grouping is kept as text, `organization>repository`, and a value saved by the one-level grouping, such as `repository`, reads as that one level. A row is kept closed by an id that names its place, such as `organization:acme|repository:acme/api`. A one-level grouping gives the same ids the sectioned list did, so rows closed before stay closed, and an id with no row now does nothing. When the grouping changes and a selected title row no longer exists, the first pull request it held is selected.
  - It is `ListGrouping` and `ListTree` in the core library: the choice, the tree, the counts, and the pure parts of opening, closing and moving the selection. It arranges rows and keeps none out. It is not a filter and has no syntax.
- A selected title row shows an overview of what it holds (MAC-114, Figma row 10)
  - The owner asked for "an overview of the set of PRs. perhaps in grid of cards that preview them? final form TBD", reviewed the design, and chose cards for now. A table or list may come later for very large sets. The "Needs decision" cards on the row were built as proposed and the owner has not decided them: what the overview is made of, what a card shows and what a click does, and whether it follows the search and the filter.
  - It is a layout of blocks, so nothing on it has a fixed place. The page's `PageLayout` and `BlockKind` place blocks that each draw one pull request, so the overview has its own, `OverviewLayout` and `OverviewBlockKind`, the same shape at its smallest: an id, a name, and blocks top to bottom, each a kind and a `BlockSize`. The kinds are `summary` and `pullRequests`. One layout is built in, "Overview": the summary, then the pull requests, both large. It is compiled in, not a file in the configuration folder, since nothing can change it yet. Columns, tabs, a file, `ctl` and MCP come with Edit Layout and build on this shape. Every block works at both sizes: a small summary is the name and one line of counts, and small cards are the title, badge and number.
  - It reads the tree the list draws (`GroupOverview` in the core library), so it holds exactly the rows under the selected row, within the chosen tab, a filter applied on it and the search, and its counts match the list's. When the search or a filter applied on the tab narrows it, a line under the count says so and how many the row holds in the tab's own saved filter without them: "Narrowed by the applied filter: 72 of 213 shown". The tab itself does not count as narrowing, since choosing a tab is choosing what to look at, as choosing a view was. This was chosen on the owner's behalf when MAC-113 met MAC-114, for him to overrule. An applied filter takes the place of the tab's own and can hold more, so the line shows only when the row holds fewer.
  - The summary: the row's symbol and name, in full for a repository ("acme/api") or its shorthand with the full name on hover; its kind and count, "Organization · 11 open pull requests in 4 repositories"; then tiles. "Your review" counts the pull requests that ask a review of the viewer or one of the viewer's teams, outlined in the accent color, since someone waits on the viewer. "Your move" counts the viewer's own that wait on the viewer, other than drafts. Then one tile per status that has any, in the badges' order and colors. The tiles wrap.
  - The sections are the title rows one level down, such as each repository of an organization, each headed by its name (with its shorthand, as the list names it), its count, and a badge per status. A click on a heading selects that row. At the last level of the tree there is nothing below, so the cards are put in sections by status in the badges' order, headed by the status's long name, unless the row or one above it is a status; then there is one section with no heading. Within a section cards keep the list's order, most recently updated first.
  - A card: the title, up to two lines, with the status badge at its right; the number, the author ("you" for the viewer) and how long since it was updated, with the repository in front only when no heading names it and the author left out under an author's row, shorthands in place of names as in the list; the status's detail line; and at its foot whose move it is and the lines added and removed. Whose move it is follows the status: the author for draft, blocked, changes requested, a failed check that is not required, threads, behind and ready; the reviewers asked, a team as one, for waiting; CI for running and queued; the merge queue; GitHub while it checks for conflicts. The viewer reads "you" and a team the viewer is on is drawn in the accent color. At most two reviewers are named, then "+N", and the tooltip names everyone in full. Under an author's row the author reads "the author". When a review is asked of the viewer and the line does not already name them, a "your review" tag follows. The card's tooltip has the full title, reference, author, status sentence, when it was updated and opened, and its checks. Drafts are drawn a little faded.
  - Checks are not drawn on the card apart from the tooltip, because the status's badge and detail already say when a check failed, runs or waits, and repeating it is noise.
  - A click on a card selects its pull request in the list, which opens the rows above it, and shows its page.
  - The grids are lazy, so an organization of about 200 in "Everything open" builds only the cards on screen. Cards are at least 270 points wide and fill the row, and the page is at most 1,400 points wide.
- A list row has three lines and a badge (MAC-69)
  - The title, which wraps to a second line when it must. Then the repository and number with the author, where a long repository name gives way in the middle and the author is left out before the number is hidden. Then the status's detail, such as "e2e-chrome failed, 3 threads unresolved". A short badge in the color of its tone sits at the right of the second and third lines.
  - The badge and the detail come from `StatusSentence`. The badges are Draft, Merging, Blocked, Changes, Running, Failing, Threads, Waiting, Behind, Checking, Ready, Merged and Closed. CI running and checks queued are both Running, and waiting on reviewers and needing a review are both Waiting. The detail does not repeat the badge and leaves out "Review requested from you".
- The list's width follows a drag on its trailing edge (MAC-55)
  - From 260 to 480 points, 300 by default. Double-clicking the edge puts it back to 300. In a small window the list gives way so the page keeps at least 600 points, without forgetting the width chosen.
- Window state is not configuration (MAC-55)
  - The list's width, the chosen tab, the grouping, the closed rows of the tree and the selection are remembered across launches in `UserDefaults`, as window state: where the person left the window. They are not settings, so they are not files in the configuration folder and not reachable from the command line or MCP. Anything that changes what the app does still belongs in the configuration folder.
- The diff is a stack of panes over the page
  - After Figma row 8 and the owner's note on MAC-53: the diff comes over the pull request without leaving it. Selecting a file in the Files block slides its diff in from the right, and a review thread slides in over the diff. Built for trial; the owner has not chosen between this and a diff tab.
  - The stack is `PaneStackPath` and `PaneStackLayout`, ported from `mac-os-agent`'s Settings, copied rather than shared. The page's blocks are the base. A path entry is `file:<path>` or `thread:<id>` (`PullRequestPane`).
  - The header (repository and number, title, status sentence, action buttons) is never covered. Panes cover the area below it, down to the window's bottom edge, since MAC-55 removed the footer. With a layout of tabs, the tab strip is part of what a pane covers, because the tabs choose blocks and the panes go over blocks. The pull request list stays as it is.
  - A pane is a card with a rounded top-leading corner and a shadow to its left, 10 points below what it covers. A covered pane is dimmed, does not scroll or take clicks, and is hidden from accessibility apart from a "Back to" button. A click anywhere on its strip goes back to it. The open file's row in the Files block stays marked.
  - Escape closes one pane, and so does the pane's back button ("‹ Pull request", "‹ Files"). With no pane open, Escape does what it did before. Panes slide with a 0.28-second spring with no bounce, or fade with Reduce Motion.
  - The panes belong to the selected pull request. Choosing another closes them.
  - Clicking a thread in the Threads block opens its file's diff with the thread on top, scrolled to its line. A thread whose file is not among the changed files does not open.
  - The thread pane is 420 points: the file and line, the quoted line, each comment with its author and age, and a Reply field with Resolve and Reply, disabled with the same read-only note as the action buttons.
- The diff pane's width rule
  - The page's strip is 300 points. It narrows to a 24-point sliver in side by side mode, with a thread open, or when a full strip and a 220-point file tree would leave the diff less than 720 points. Then the tree narrows to a 40-point rail, in side by side mode or when the full tree would still leave less than 720. The page gives way before the tree, as the oldest strip does in the stack. `DiffPaneLayout` holds the rule, and `PaneStackLayout` has the last word in a very narrow window.
  - At the app's default size, with the list showing, the page is a sliver even inline: 1,180 points less 300 and 220 is under 720.
  - The rail shows each file as a mark for its kind of change: a pencil for modified, plus for added, minus for deleted, an arrow for renamed, a picture for binary. Folders are separated by a line. The full path, kind and counts are in its tooltip, and the open file is filled with the accent color. Initials, as the Figma frame draws them, were left out as too cryptic.
- Inline and side by side
  - Inline is one column: old and new line numbers, then `−` or `+`, then the line. Removed lines are pale red and added pale green, and the symbol is always drawn beside the color. Hunk headers are shown as written.
  - Side by side puts the old file on the left and the new on the right. Inside a hunk, a run of removed lines pairs line for line with the run of added lines after it, and the longer run's extra lines face blank filler. Context lines face themselves. Each hunk's header shows its old and new line ranges.
  - Long lines scroll sideways and never wrap. The line numbers, markers and thread markers stay put and only the code moves, so in side by side both halves stay on screen and scroll together.
  - The diff is built once per file, off the main thread, from the parsed patch (`DiffDocument`), and kept while the window is open. Every row has the same height and width, so nothing is measured per row. The 5,000-line mock patch builds in about 20 milliseconds in a debug build.
  - Code is tinted on a best-effort basis, a line at a time, with no dependency: keywords, strings, comments and numbers for TypeScript-like files, and strings, numbers and `#` comments for YAML, Terraform and shell. Anything else stays plain.
  - A line with review threads shows "1 thread · Ada Park", the count and who started the first thread, at its end. It opens that thread. Binary files say "Binary file, not shown", a pure rename says so, and added, deleted and renamed files are tagged in the file header.
- A thread needs the viewer as code owner
  - Besides the viewer's own pull requests, threads they commented in, and mentions, a thread needs the viewer when a review is asked of them, or of a team they are in, and that person or team owns the thread's file by CODEOWNERS. So two of `acme/api #4826`'s threads, on `auth/` owned by `@acme/security`, need the viewer, and Max's on `api/routes/login.ts` waits on the author.
- Renders are drawn offscreen

- There is one filter language, and its first form is built (MAC-112)
  - A filter is sets of conditions. A pull request matches when any set matches, and a set matches when every condition in it does. A condition tests one field with "is" or "is not" against one or more values, and the values are alternatives. Sets do not nest. No sets, or a set with no conditions, matches everything. This answers the Figma row 11 card "How far does OR go?" as it proposed.
  - It grew out of the filter menu's clause, "field is one of values" (`ListFilter.Clause`), which is now the language's `FilterCondition`. The extension is the smallest that carries saved filters: an operator on each condition, sets joined by OR, the field `organization`, the review state `waitingOnMe`, and the author `@me`. There is no second representation of a condition: the menu, saved filters, `ctl` and MCP all use this one, and search and layout rules are to use it too.
  - The fields are status (the badge, such as `blocked`), organization, repository (`owner/name`), author (a login, or `@me` for the viewer), review state (GitHub's decision, or `waitingOnMe` when a review is asked of the viewer or one of the viewer's teams), and draft (`true` or `false`). Organization, repository and author ignore case. A new field, such as label, path or checks, is a new case of `FilterField` with its values, its check and its words, and nothing else changes.
  - Waiting on me is a review state beside the decision, as Figma row 11 draws it, so a pull request can be both `reviewRequired` and `waitingOnMe`.
  - In JSON a filter is `{"sets": [{"conditions": [{"field": "status", "operator": "is", "values": ["blocked"]}]}]}`. `operator` may be left out and is then `is`. A filter read from a file, `ctl` or MCP goes through the same checks, which name where a problem is, such as `sets[0].conditions[1].values[0]`.
  - Evaluation gives the matches, how many there were to start with, and a count by status in the badges' order: "7 of 218 match, 3 blocked · 2 waiting · 2 ready".
  - A filter can be said in plain words: each set is a sentence, its conditions joined by "and" when there are two and by commas when there are more, and sets after the first start with "Or". For example "Blocked or changes requested, in acme/api or acme/web, not by dependabot. Or waiting on me and not a draft."
